# 0004 — E2E contra Nextcloud real (T18)

Decisiones tomadas sin supervisión. Se deshacen con `git revert` del PR.

| # | Decisión | Motivo |
|---|---|---|
| 1 | Imagen `nextcloud:33.0.9-apache` fijada, SQLite, sin volúmenes, solo en `127.0.0.1:8080`. | Reproducible y desechable (`down` lo borra). Con 33.0.9 la app Notes 6.1.0 se instala desde la tienda sin problemas. |
| 2 | Contraseña de admin fija en el compose (`admin-e2e-only`). | Solo escucha en localhost y se destruye; la contraseña de aplicación se crea por OCS (`core/getapppassword`) y es lo que usa el cliente, como en producción. |
| 3 | Los tests viven en `app/src/test/.../e2e` con `@Tag("e2e")`; `test` los excluye y `./gradlew e2eTest` (tarea `Test` que reutiliza clases y classpath de `testDebugUnitTest`) solo los incluye. | Un único módulo Android: un source set aparte exigiría duplicar la configuración de AGP/Kover. |
| 4 | Sin variables de entorno los tests se saltan (`assumeTrue`), no fallan. | `e2eTest` es inocuo en una máquina sin servidor. |
| 5 | Si `NC_URL` no es localhost y no hay `E2E_ALLOW_REMOTE=1`, la suite falla antes de tocar nada (con test unitario normal en `check`). | Evitar borrar notas de un servidor real por error. |
| 6 | Todo se llama `[test]...` (títulos y carpetas); antes y después de cada test se borran por API las notas `[test]`. | Regla de CLAUDE.md; las carpetas vacías que deja Nextcloud no se limpian. |
| 7 | `SyncFixture` acepta ahora un `NotesClient` (el constructor antiguo con `FakeNotesServer` sigue igual). | Reutilizar los mismos helpers de "usuario" en unitarias y E2E. |
| 8 | "Offline" se simula no llamando a `sync()`; no se corta la red. | Es lo que hace el motor: la cola vive en Room. |
| 9 | Workflow `e2e.yml` aparte, no requerido: PR que toca `data/`, `sync/`, `e2e/`, nocturno y manual. | Arranca un servidor (~3 min) y depende de versiones externas. |

## Resultado de la primera ejecución real (Nextcloud 33.0.9, Notes 6.1.0, Docker local)
20 tests E2E en verde. Confirmado contra el servidor real: `If-Match` entrecomillado, 304 de la lista,
`chunkSize`/cursor, título saneado y numerado `(2)` adoptado, recorte a 100 caracteres, carpetas y
subcarpetas, favoritos, copia de conflicto sin pérdida de texto, DELETE en servidor + edición offline
(recrea), CRLF/emoji/Unicode/tablas/HTML idénticos byte a byte, 401 con contraseña incorrecta.
No se encontró ningún fallo del cliente que obligara a cambiar código.

## Limitación conocida (no corregida)
Si un cliente solo cambia favorito o carpeta y otro edita el texto de la misma nota, el 412 se resuelve
como conflicto de texto (el motor no guarda el texto base): no se pierde nada, pero aparece una copia
`(conflicto fecha)` del texto sin cambios. Arreglarlo exige guardar el texto (o su hash) del último
estado sincronizado: columna nueva + migración de Room. Queda fijado por el test
`a favorite racing a remote edit loses nothing and both clients converge`. Pendiente decidir.
